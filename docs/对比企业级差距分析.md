# 对比企业级差距分析（面试追问概率 × 补齐成本 排序）

> 评估基准：2026-10-26 的 main 分支（R1–R5 已落地）。
> 定位：练习仓目标是「面试佐证」而非真实生产，因此排序 = 面试官追问概率 × 补齐成本，**不追求补全**。
> 每项给出：现状（仓库证据）→ 企业级标准 → 追问概率 → 补齐成本 → 建议动作。

---

## 〇、总览矩阵

| # | 维度 | 追问概率 | 补齐成本 | 本轮建议 |
|---|------|---------|---------|---------|
| 1 | 可观测性纵深 | ★★★★★ | 中（3-4 晚） | **做**（M3 计划项） |
| 2 | 数据层单点 | ★★★★ | 高（真实主从/备份要资源） | 讲清楚 + 做最小版 |
| 3 | 安全 | ★★★★ | 低-中 | 挑便宜的做 |
| 4 | 降级预案层 | ★★★ | 低（代码量小） | 做（1 晚） |
| 5 | 工程效率 | ★★ | 中 | 只讲不做的部分写进文档 |
| 6 | 业务纵深 | ★★ | 高 | **明确不做**（定位原因写文档） |

## 一、可观测性纵深（当前最大空白，追问概率最高）

面试逻辑：R1–R5 的所有机制——预扣额度对不对、租约有没有泄漏、对账差异抓没抓到——**全部依赖"看得见"才可信**。追问"你们怎么知道 Lua 预扣生效了？"答不出指标就是硬伤。

### 1.1 链路追踪（现状：接了但断链）

- **现状**：`pkg/tracing/tracing.go` 已接 zipkin exporter v1.47；gateway/order 等服务挂了 otelgin 中间件；但 **trace 上下文没有跨层穿透**——HTTP→gRPC（无 metadata 注入）、gRPC→RabbitMQ（消息体无 trace 字段）、MQ→消费者（无提取），一条订单链在追踪系统里是 4 段孤立的 trace。
- **企业级标准**：OTel 全链路——HTTP header（traceparent）/ gRPC metadata（client/server interceptor）/ MQ 消息体（AMQP headers）三层透传；Jaeger/Tempo 一条链从 Client 点到 MQ 消费者查到底。
- **追问概率**：★★★★★（"画一下你们的一次下单全链路，怎么排查慢在哪一跳？"）
- **补齐成本**：3-4 晚。具体：gRPC client/server interceptor 注入提取 traceparent（`pkg/tracing/grpc.go` 已有骨架）＋ MQ 发布时写 AMQP header、消费时提取重建 context ＋ Jaeger 收集端（docker-compose 加 jaeger-all-in-one）。
- **建议动作**：做。这就是 M3 计划项。

### 1.2 指标（现状：半成品）

- **现状**：9 个服务都有 `/metrics`（promhttp）；outbox 有 4 个专属指标（pending/成功/失败/DLQ）；但 **HTTP RED（请求数/错误率/延迟直方图）记录在 `pkg/middleware/metrics.go` 的内存 JSON collector 里，没有导出成 Prometheus 指标**——即 Grafana 抓不到请求级数据。
- **企业级标准**：RED（服务级）+ USE（资源级）全量 Prometheus 化；Grafana 看板随代码走（dashboard as code，JSON 进仓库）。
- **追问概率**：★★★★（"你们上线后看哪几个面板？告警阈值怎么定的？"）
- **补齐成本**：1 晚。把 `middleware/metrics.go` 的 RecordRequest 改写成 Prom CounterVec/HistogramVec（http_requests_total{method,path,status}、http_request_duration_seconds histogram），删内存 collector。
- **建议动作**：做，性价比最高的单项。

### 1.3 告警（现状：零）

- **现状**：无任何告警规则、无 AlertManager。
- **企业级标准**：错误率>1% 持续 5min、P99 延迟越界、RabbitMQ 积压>1000、Outbox PENDING>500、分发队列 QUEUED 堆积、reconcile_diff 新增突增——分级路由（P0 电话、P1 IM、P2 邮件）。
- **追问概率**：★★★★（"凌晨三点对账发现 100 条差异，流程是什么？"）
- **补齐成本**：1 晚（规则文件 + compose 里挂 AlertManager；通知渠道练习仓可以只落文件不接真实 webhook，文档写明差异）。
- **建议动作**：做规则文件（即无接收端也算落地，能讲）。

### 1.4 日志（现状：单机）

- **现状**：Zap 结构化日志输出到 stdout，无收集。
- **企业级标准**：Loki/ELK 收敛 + trace_id 关联查询。
- **补齐成本**：真实部署要资源，练习仓 docker-compose 加 loki+promtail 即可"架构完整"。
- **建议动作**：compose 加一行 + 文档写清，不深做。

## 二、数据层：单点一切（第二梯队）

### 2.1 MySQL 单实例

- **现状**：所有服务共享单实例 MySQL（演示栈里复用主机的 async-mysql）；无主从、无备份、无恢复演练、无慢查询治理、无归档。
- **企业级标准**：一主两从 + 半同步/组复制；每日全备 + binlog 增量（PITR 可恢复到任意秒）；慢查询日志 >100ms 周报治理；大表（订单/行为日志）按月归档或分区。
- **追问概率**：★★★★（"MySQL 挂了怎么办？RPO/RTO 多少？"——这是分布式加分题的入口）
- **补齐成本**：真实搭建高（需要资源）；**文档+脚本版低**——写《数据可靠性设计》文档 + mysqldump/xtrabackup 脚本进仓 + 一次恢复演练记录。
- **建议动作**：做文档+脚本+演练记录（1 晚），真主从不搭（写明差异）。

### 2.2 Redis 单节点

- **现状**：单节点无持久化配置审查；**R1 的预扣额度和流水在 Redis 上**——Redis 挂掉=额度丢失（对账兜底可恢复真账，但正在途的流水会丢）。
- **企业级标准**：AOF everysec + 主从+哨兵（或 Cluster）；预扣类热点 key 的持久化等级单独评估。
- **追问概率**：★★★★（"Redis 挂了库存怎么办？"——正好引出对账兜底的叙事）
- **补齐成本**：compose 版哨兵半天；文档半天。
- **建议动作**：文档为主（把"Redis 挂了 → 对账兜底 → 额度从 DB 重新惰性加载"写进 R1 文档，这本身就是好的面试答案），compose 可选。

### 2.3 迁移发布纪律

- **现状**：版本化 migration 齐全（000001-000006）+ CI 幂等校验；但无 staging 先行、无生产变更窗口、无回滚演练。
- **建议动作**：写进《数据库变更流程》文档（1 小时），不搭环境。

## 三、安全（追问概率高、单件成本低）

| 项 | 现状 | 企业级标准 | 追问 | 成本 | 动作 |
|----|------|-----------|------|------|------|
| 服务间加密 | gRPC 全明文（insecure credentials 遍布 grpc_client.go） | 内网 mTLS 或至少 TLS | ★★★ | mTLS 高（证书体系），TLS 低 | 做 TLS 单向（1 晚）+ 文档写 mTLS 演进 |
| Token 体系 | JWT 2h 硬过期，无 refresh | access+refresh 双 token + 轮换 + 登出全端失效 | ★★★★ | 1 晚（refresh 接口 + redis 存 refresh token） | 做（auth 包现成，顺路） |
| RBAC | `pkg/middleware/rbac.go` 写了未挂载 | admin 路由按角色强制 | ★★★ | 半天（admin 组挂 RBAC 中间件） | 做 |
| 供应链 | 镜像无签名无 SBOM（trivy 还在非阻断） | cosign 签名 + SBOM + 基线扫描阻断 | ★★ | 高 | 文档提及即可 |
| 密钥治理 | K8s Secret 已有；本地 env 有明文 | 密钥轮换 + 禁止入仓 | ★★ | — | 已有基本盘，保持 |

## 四、流量治理的"预案"层（限流熔断都有了，缺降级）

- **现状**：网关限流、每依赖熔断（resilience.CircuitBreaker）、三层幂等都在；但**没有任何降级预案**：推荐服务挂了首页空白？库存预扣超时了下单直接报错给用户？
- **企业级标准**：每条链路写"降级开关 + 降级行为 + 演练记录"——推荐挂了→回退热卖榜静态数据；库存预扣超时→**快速失败并幂等可重试**（而不是同步等待拖死网关）；对账服务挂了→告警但不阻断主链路。
- **追问概率**：★★★（"你们的熔断打开之后用户体验是什么？"）
- **补齐成本**：1 晚（推荐代理处加 fallback 到 cold-start 静态数据；预扣超时路径确认快速失败；文档《降级预案》一页纸）。
- **建议动作**：做，与 R1-R5 叙事直接咬合。

## 五、业务纵深（差距最大，**明确不做**）

支付仅状态机 mock（无渠道接入/渠道对账/结算分账）、无拆单、无风控（防刷/设备指纹/黑名单）、无逆向流程（收货后退换货、价保）、无履约仓储。

**不做的原因（写进文档的诚实声明）**：练习仓定位是**链路工程佐证**——服务拆分、一致性、幂等、限频、对账。业务堆料（加十个领域模块）不增加工程说服力，反而稀释。面试遇到业务追问的正确姿势：讲清楚"支付渠道对账和我 R4 的库存对账是同构模式，真实业务里套同一个台账状态机"。

## 六、工程效率（有更好，优先级最低）

配置中心（Apollo/Nacos，现在是 env+ConfigMap）、GitOps（Argo CD，现在是 GH Actions push 部署）、feature flag、多环境隔离（dev/staging/prod 拆分未勾选）、服务网格。

**建议动作**：不实现；在 README/docs 里写一节"如果迁移到企业环境会怎么演进"——这比半吊子实现更能体现架构判断力。

## 七、结论：下一轮行动清单（按本排序）

| 优先 | 动作 | 成本 |
|------|------|------|
| 1 | HTTP RED 进 Prometheus（1.2） | 1 晚 |
| 2 | OTel trace 三层穿透 + Jaeger（1.1） | 3-4 晚 |
| 3 | 告警规则 + AlertManager（1.3） | 1 晚 |
| 4 | RBAC 挂载 + refresh token + gRPC TLS（三、挑便宜的） | 2 晚 |
| 5 | 降级预案：推荐 fallback + 预扣快速失败确认 + 文档（四） | 1 晚 |
| 6 | 数据可靠性文档 + 备份脚本 + 恢复演练记录（2.1/2.2） | 1 晚 |
| 7 | 演进声明文档（五/六） | 2 小时 |

合计约 9-11 晚，完成后"对比企业级还差什么"的可答清单只剩：真实主从/多可用区、mTLS/供应链、业务纵深、配置中心——全部可以用"知道差距 + 写了演进方案"的话术覆盖。
