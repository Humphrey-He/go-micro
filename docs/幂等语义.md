# 幂等语义说明（三层幂等体系）

> R2 产出 · 对应「请求级防重放、业务级防重复、兜底是唯一索引」经历锚点
> 代码：`pkg/middleware/idempotency.go`（请求级）· 各服务唯一索引（业务级）· `pkg/idemp/consumer.go` + `consumed_messages`（消费级）

---

## 一、三层各自防什么

| 层 | 防的问题 | 机制 | 失效兜底 |
|----|---------|------|---------|
| 请求级（gateway） | 网络重试/客户端重放导致**同一 HTTP 请求**重复执行 | Redis 响应快照：首次成功响应缓存 24h，重放直接返回首次响应（`X-Idempotency-Replayed: true`） | 业务级唯一索引 |
| 业务级（服务内） | 请求级缓存过期/未命中时**同一业务单据**重复创建 | `orders.idempotent_key`、`order_no`、`payments.request_id` 唯一索引，撞键拒绝 | — |
| 消费级（MQ 下游） | MQ at-least-once 导致**同一消息**重复消费 | `consumed_messages(consumer_group, message_id)` 唯一索引，`INSERT IGNORE` 撞键跳过 | — |

## 二、请求级幂等键优先级

1. `X-Idempotency-Key` —— 客户端显式声明（推荐支付等关键操作携带）
2. `X-Request-Id` —— 网关每请求注入的标识，拼接 `method:path` 防跨接口碰撞
3. 兜底哈希 —— `sha256(method + path + Authorization + body)`；
   **授权头参与哈希**，不同用户提交相同 body 不会被误判为重放

## 三、语义定义（覆盖 vs 累加）

- **响应语义 = 覆盖（replay）**：重放返回**首次的完整响应快照**，不重新执行、不累加。
  同一请求打 5 次 → 业务执行 1 次、5 次响应逐字节相同（验收用例
  `TestIdempotency_ReplayFiveTimesSameResponse`）。
- **在途语义 = 拒绝（409）**：首次请求仍在处理中时，同键请求返回
  `409 {code:40901}`，客户端应退避后重试（可重放语义，非并发执行）。
- **失败语义 = 放行重试**：首次响应 ≥400 时**不缓存**快照并清除 pending，
  允许客户端修正后重试；下一次成功才建立快照。
- **消费语义 = 吸收（absorb）**：重复投递的消息在 `consumed_messages`
  撞键后直接 ACK，不执行业务——与生产侧 Outbox 的 at-least-once 组合成
  「业务恰好一次」（限边界：消费处理到一半崩溃时由下游业务级唯一索引兜底）。

## 四、挂载范围

网关已挂请求级幂等的创建类路由：`POST /orders`、`POST /payments`、
`POST /payments/:id/{success,failed,timeout}`、`POST /refund/initiate`、
`POST /activity/{coupon,seckill}`。

**不挂**的路由及原因：
- 认证类（`/auth/*`）：密码修改后同 body 登录必须放行，缓存快照会吞掉新凭证
- 查询/计算类（GET、`/price/calculate`）：无副作用，无需付出 Redis 往返
- 验证码发送（`/auth/sms/send`）：发送冷却（60s）已是更强的业务级幂等

## 五、与真实经历的差异（诚实红线）

| 真实经历 | 本练习仓简化 |
|---|---|
| 幂等中心独立服务，按租户分桶、快照落 DB+缓存双写 | 中间件内置 Redis 单写，快照 24h TTL |
| 消费幂等表按消息分区清理（7 天滚动） | 无清理任务（后续 R 项补） |

## 六、面试话术锚

「请求级防重放、业务级防重复，兜底是唯一索引——重放返回首次响应快照；
在途请求返回 409 让客户端重试，失败响应不缓存，这样重试语义才是完备的。」
