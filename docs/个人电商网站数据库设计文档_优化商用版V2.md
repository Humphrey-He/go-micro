
# 个人电商网站数据库设计文档（优化商用版 V2）

## 1. 文档目标

本文档基于现有个人电商网站数据库设计进行工程化重构，目标是形成一份可直接用于中小型商用项目落地的数据库设计方案。设计目标如下：

1. 支持标准电商链路：注册登录、商品浏览、购物车、下单、支付、发货、签收、评价、售后、退款。
2. 保证核心域边界清晰：订单、库存、支付、售后、退款分别建模，避免状态互相污染。
3. 支持未来扩展：多商户、多仓、促销活动、消息通知、推荐分析、异步任务、分库分表。
4. 避免常见生产雷点：金额单位混乱、库存双写、退款与售后混用、日志不可追踪、幂等缺失、索引失衡。
5. 兼顾实现成本：优先采用 MySQL 8.x + InnoDB 的通用设计，不依赖过重中间件。

## 2. 设计原则

### 2.1 核心原则

- **事实唯一**：库存事实只由库存域维护；支付事实只由支付域维护；退款资金事实只由退款域维护。
- **业务单号与自增主键分离**：所有表保留 `id` 作为内部主键；对外业务标识统一使用 `*_no`。
- **金额统一单位**：所有金额字段使用 `BIGINT`，单位为最小货币单位（如分）。
- **状态机分层**：订单主状态、售后状态、支付状态、退款状态分开建模。
- **快照落库**：下单时冗余商品、价格、地址、营销信息，避免后续变更影响历史事实。
- **日志可追踪**：关键链路都保留 request_id / trace_id / operator / remark。
- **幂等优先**：下单、支付回调、退款回调、库存确认、任务执行都必须有幂等控制。
- **低频扩展放 JSON**：仅把不参与核心查询和约束的字段放进 JSON。

### 2.2 命名规范

- 用户：`user_no`
- 商品 SPU：`spu_no`
- 商品 SKU：`sku_no`
- 订单：`order_no`
- 订单明细：`order_item_no`
- 支付单：`payment_no`
- 退款单：`refund_no`
- 售后单：`after_sale_no`
- 发货单：`shipment_no`
- 优惠券模板：`coupon_tpl_no`
- 用户优惠券：`coupon_user_no`

### 2.3 通用字段规范

建议所有核心业务表统一包含下列字段中的子集：

- `id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY`
- `created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)`
- `updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3)`
- `deleted_at DATETIME(3) NULL`
- `version INT NOT NULL DEFAULT 1`
- `remark VARCHAR(255) NULL`
- `ext_json JSON NULL`

### 2.4 时间与时区

- 数据库统一存 UTC 或统一服务器时区。
- 应用展示层再转本地时区。
- 推荐使用 `DATETIME(3)` 保留毫秒级链路追踪能力。

说明：

- 主表只保留稳定身份主体，不放复杂角色、社交 token、统计字段。
- 用户名、手机号、邮箱建议允许为空，但唯一约束要结合业务策略。

```sql

    last_login_at       DATETIME(3) NULL COMMENT '最后登录时间',
    last_login_ip       VARCHAR(45) NULL COMMENT '最后登录IP',
    password_updated_at DATETIME(3) NULL COMMENT '密码最后变更时间',
    deleted_at          DATETIME(3) NULL COMMENT '软删除时间',
    created_at          DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    updated_at          DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
    UNIQUE KEY uk_user_no (user_no),
    UNIQUE KEY uk_phone (phone),
    UNIQUE KEY uk_email (email),
    UNIQUE KEY uk_username (username),
    KEY idx_status_created (status, created_at)
```

## 5.5 用户地址表

设计要点：

- 历史订单不依赖该表，地址只用于下单前选择。
- 默认地址通过程序保证同一用户仅一条。
- 采用 `deleted_at` 代替 `is_deleted`。

```sql
CREATE TABLE user_addresses (
    id                  BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    address_no          VARCHAR(32) NOT NULL COMMENT '地址编号',
    user_no             VARCHAR(32) NOT NULL COMMENT '用户编号',
    receiver_name       VARCHAR(64) NOT NULL COMMENT '收货人姓名',

    province_code       VARCHAR(16) NOT NULL,
    city_code           VARCHAR(16) NOT NULL,
    district_code       VARCHAR(16) NOT NULL,
    province_name       VARCHAR(64) NOT NULL,
    city_name           VARCHAR(64) NOT NULL,
    district_name       VARCHAR(64) NOT NULL,
    detail_address      VARCHAR(255) NOT NULL,
    postal_code         VARCHAR(16) NULL,
    address_tag         VARCHAR(32) NULL COMMENT '家/公司/学校',
    lng                 DECIMAL(11,6) NULL,
    lat                 DECIMAL(11,6) NULL,
    is_default          TINYINT NOT NULL DEFAULT 0,
    deleted_at          DATETIME(3) NULL,
    created_at          DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    updated_at          DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),

    KEY idx_user_default (user_no, is_default),
```

## 6.7 商品 SKU 表

说明：

- SKU 不存库存事实，只存售卖事实。
- 金额统一使用分。
- `status` 与 `sale_status` 可按项目复杂度合并，这里拆开便于后续运营。

```sql
CREATE TABLE product_skus (
    id                  BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    sku_no              VARCHAR(32) NOT NULL,
    spu_no              VARCHAR(32) NOT NULL,
    merchant_no         VARCHAR(32) NOT NULL,
    shop_no             VARCHAR(32) NOT NULL,
    sku_code            VARCHAR(64) NULL COMMENT '商家内部编码',
    barcode             VARCHAR(64) NULL,
    sku_name            VARCHAR(255) NOT NULL,
    currency_code       CHAR(3) NOT NULL DEFAULT 'CNY',
    sale_price          BIGINT NOT NULL COMMENT '销售价，单位分',
    market_price        BIGINT NOT NULL DEFAULT 0 COMMENT '划线价，单位分',
    cost_price          BIGINT NOT NULL DEFAULT 0 COMMENT '成本价，单位分',
    tax_rate            DECIMAL(6,4) NOT NULL DEFAULT 0.0000 COMMENT '税率，如0.1300',
    weight_gram         INT NOT NULL DEFAULT 0 COMMENT '重量，克',
    volume_cm3          INT NOT NULL DEFAULT 0 COMMENT '体积，立方厘米',
    sale_status         TINYINT NOT NULL DEFAULT 1 COMMENT '1可售 2不可售',
    status              TINYINT NOT NULL DEFAULT 1 COMMENT '1正常 2禁用 3删除',
    is_default          TINYINT NOT NULL DEFAULT 0,
    sold_count          BIGINT NOT NULL DEFAULT 0 COMMENT '展示销量，异步汇总',
```

## 8. 订单域设计

## 8.1 订单状态设计

### 订单主状态 `order_status`

- `created`：订单已创建
- `pending_payment`：待支付
- `paid`：已支付待发货
- `partially_shipped`：部分发货
- `shipped`：全部已发货
- `completed`：已完成

- `closed`：已关闭（终态）

- `none`：无售后

## 10. 库存域设计

## 10.1 设计原则

1. 库存事实只在库存域维护。
2. SKU 主表不再存强一致库存。
3. 库存变更动作应标准化为：
   - `reserve` 预占
   - `confirm` 确认预占
   - `release` 释放预占
   - `deduct` 扣减
   - `return` 归还
   - `adjust` 调整

## 11. 支付域设计

## 12. 售后与退款域设计

## 12.1 设计原则

1. 售后流程与资金退款分离。
2. 售后单解决业务审核、退货、换货、补发。
3. 退款单只解决资金退回。
4. 部分退款要在订单明细级追踪。
5. 售后和退款都应支持重试和日志追踪。

## 20. 关键生产问题与本版规避方式

### 20.1 金额单位混乱

**问题**：部分表写元，部分表写分，退款和支付极易错账。  
**方案**：本版统一所有金额字段为 `BIGINT`，单位为分。

### 20.2 SKU 表与库存表双写库存

**问题**：高并发下 `product_skus.stock` 与 `inventory.available_stock` 不一致。  
**方案**：SKU 不再保存强一致库存，库存只在 `inventories` 中维护。

### 20.3 订单状态与售后状态混用

**问题**：部分退款、部分售后无法准确表达。  
**方案**：订单主状态与售后聚合状态分开；售后真实状态落到 `after_sale_orders` 和 `after_sale_items`。

### 20.4 售后与退款表职责重叠

**问题**：仅退款、退货退款、换货、补发混在一起，链路难以维护。  
**方案**：售后单解决业务流程，退款单解决资金流程。

### 20.5 支付回调重复通知导致重复记账

**问题**：微信、支付宝常见重复通知。  
**方案**：引入 `payment_callbacks`，以 `channel_code + callback_id` 做唯一去重。

### 20.6 优惠分摊只存在 JSON 中

**问题**：退款和对账时难以准确回退。  
**方案**：新增 `order_discount_details`，结构化记录每笔分摊。

### 20.7 发货链路缺失

**问题**：只能表达整单发货，无法部分发货、拆包发货。  
**方案**：新增 `shipments` 与 `shipment_items`。

### 20.8 用户主表过胖

**问题**：社交、统计、安全字段混合，读写压力大。  
**方案**：拆分为 `users / user_profiles / user_security / user_stats`。

## 21. 索引设计建议

### 21.1 原则

1. 避免只给低区分度状态字段单独建索引。
2. 索引围绕查询路径设计，而不是围绕字段“看起来重要”设计。
3. 列表查询常用组合：
   - `(user_no, created_at)`
   - `(status, created_at)`
   - `(shop_no, status, created_at)`
4. 对账和回调常用组合：
   - `(channel_code, channel_trade_no)`
   - `(channel_code, callback_id)`

### 21.2 分页优化建议

大表列表分页尽量采用：

- `WHERE created_at < ? ORDER BY created_at DESC LIMIT 20`
- 或基于 `(id, created_at)` 游标翻页

避免深分页 `OFFSET`。

## 22. 分库分表建议

当前个人站可先不做，但需要提前预留：

### 22.1 优先预留分表的表

1. `orders`
2. `order_items`
3. `payments`
4. `refunds`
5. `inventory_logs`
6. `user_behavior_logs`
7. `notifications`

### 22.2 推荐拆分策略

- `orders`：按用户维度分库，按月份分表
- `order_items`：跟随订单路由
- `payments`：按订单/用户维度路由
- `user_behavior_logs`：按天分表或直接进分析型存储
- `inventory_logs`：按 SKU 或按月分表

### 22.3 业务编号要求

如未来分库分表，所有 `*_no` 应为全局唯一，建议采用：

- 雪花 ID
- 号段模式
- Redis + DB 号段发号器
- Leaf / Sonyflake / 自研发号器

## 25. 结论

本版文档适合作为个人电商网站向“可商用、可扩展”的数据库设计升级方案。它并不是为了追求绝对复杂，而是在保持实现成本可控的前提下，重点修复真实生产中最容易爆炸的几个区域：

- 金额单位
- 库存一致性
- 支付幂等
- 售后与退款边界
- 订单状态污染
- 发货链路缺失
- 优惠分摊不可追踪

如果按本版执行，即使项目先以单商户、单仓、单体服务启动，后续继续扩展到多商户、活动营销、高并发支付、异步事件驱动时，也不需要推倒重来。
